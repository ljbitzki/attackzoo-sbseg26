# AttackZoo CLI Reference

This document describes the capabilities of `attackzoo.py`, the main command-line interface for AttackZoo. It is intended as a detailed operational reference for users, reviewers, and maintainers.

For installation, safety guidance, artifact-review claims, and the reduced lab profile, see the root `README.md` and `contrib/docs/REDUX_LAB.md`.

## Overview

`attackzoo.py` is a compatibility entry point that dispatches to the implementation under `modules/attackzoo/`. It exposes commands for:

- checking local prerequisites;
- listing the dynamically loaded attack catalog;
- running and stopping individual attack containers;
- inspecting attack containers and logs;
- listing PCAP captures;
- extracting traffic features from PCAP files;
- building unsupervised dataset CSV files;
- running structured warmup/attack/cooldown experiments;
- regenerating reports from stored experiment outputs.

General form:

```bash
python3 attackzoo.py <command> [options]
```

Top-level commands:

```text
status
list
captures
features
dataset
report
experiment
run
stop
ps
logs
```

The parser accepts known options for each subcommand. For `run`, additional dynamic attack parameters are accepted through `parse_known_args()` and resolved against the selected attack's `attack.yaml`.

## Typical Workflows

### Inspect The Environment

```bash
python3 attackzoo.py status
python3 attackzoo.py list
python3 attackzoo.py list --id dos_http_simple
```

### Run One Attack Directly

```bash
python3 attackzoo.py run dos_http_simple --target 172.17.0.2 --port 80 --duration 10
python3 attackzoo.py ps --all
python3 attackzoo.py logs dos_http_simple --tail 50
python3 attackzoo.py stop dos_http_simple
```

### Generate Features And A Dataset From A PCAP

```bash
python3 attackzoo.py features --pcap captures/example.pcap
python3 attackzoo.py dataset --pcap captures/example.pcap
```

### Run A Structured Experiment

```bash
python3 attackzoo.py experiment \
  --attack-id dos_http_simple \
  --out smoke_http \
  --runs 1 \
  --levels L0,L1 \
  --warmup 5 \
  --attack 5 \
  --cooldown 5 \
  --probes http \
  --http-url http://127.0.0.1:8080/ \
  --iface lo \
  --bpf "tcp port 8080" \
  --extract-features \
  --build-dataset
```

## Common Concepts

### Attack IDs

Attack IDs are loaded from `docker/attackers/*/attack.yaml`. Use:

```bash
python3 attackzoo.py list
python3 attackzoo.py list --id <attack_id>
python3 attackzoo.py list --json
```

Examples include `dos_http_simple`, `bf_ssh`, `web_sql_injection`, and `iot_mqtt_publisher`.

### Dynamic Attack Parameters

The `run` command supports general aliases:

- `--target`
- `--port`
- `--duration`
- `--rate`

It also accepts additional attack-specific parameters declared in `attack.yaml`, such as:

- `--target_ip`
- `--target_port`
- `--target_net`
- `--duration_s`
- `--rate_pps`
- `--threads`
- `--concurrency`
- `--delay_ms`
- `--payload_size`

Dynamic parameters are not shown in the static `run --help` output because they depend on the selected attack. Use `python3 attackzoo.py list --id <attack_id> --json` to inspect them.

### Parameter Validation

Attack parameters can be validated by type or by a custom regex from `attack.yaml`.

Supported parameter kinds include:

| Kind | Validation behavior |
| --- | --- |
| `ip` | Accepts IPv4-like values and host/domain-like strings. |
| `cidr` | Accepts IPv4 CIDR strings such as `172.17.0.0/16`. |
| `port` | Requires an integer from `1` to `65535`. |
| `int` | Requires a non-negative integer. |
| `float` | Requires a non-negative number. |
| `text` | No built-in type validation unless `validate` is provided. |

### Docker Network Mode Selection

When an attack target resolves to loopback, such as `127.0.0.1` or `localhost`, and the attack also has a port parameter, AttackZoo selects Docker `host` networking automatically unless the attack metadata explicitly declares another `docker_network`.

This behavior allows attack containers to reach host-exposed services through loopback when appropriate.

### Experiment Phases

The `experiment` command divides every run into three phases:

| Phase | Purpose |
| --- | --- |
| `warmup` | Baseline measurement before attack traffic starts. |
| `attack` | Attack window; hooks are started for non-`L0` levels. |
| `cooldown` | Post-attack observation window. |

Level `L0` is treated as a baseline. Attack hooks are not called for `L0`.

### Output Directories

Common output directories:

| Directory | Purpose |
| --- | --- |
| `captures/` | PCAP files listed by `captures`. |
| `features/` | Standalone feature CSVs generated by `features`. |
| `datasets/` | Standalone unsupervised dataset CSVs generated by `dataset`. |
| `experiments/<out>/` | Structured experiment outputs. |
| `experiments/<out>/reports/` | Experiment reports regenerated or produced after experiments. |

| --- | --- | --- | --- |

| `--id ID` | no | empty | Filters to a single attack ID. |
| `--json` | no | false | Emits structured JSON instead of human-readable text. |

### Human-Readable Output

The default output groups attacks by category and prints each attack ID, name, and resolved parameter list.

Example:

```bash
python3 attackzoo.py list --category "Denial"
```

JSON output includes:

| Field | Description |
| --- | --- |
| `id` | Attack ID used by CLI commands. |
| `name` | Human-readable attack name. |
| `image` | Docker image name. |
| `container` | Docker container name used by AttackZoo. |
| `params` | Attack parameter schema, including aliases such as `target`. |
| `mitre` | MITRE metadata declared in `attack.yaml`. |
| `max_runtime_s` | Suggested max/default runtime from metadata. |

Use this output to discover attack-specific parameters for `run`.

```bash

```

## Command: `run`

Starts one attack container directly by attack ID.

```bash
python3 attackzoo.py run <attack_id> [--target IP_OR_HOST] [--port PORT] [--duration SECONDS] [--rate PPS] [dynamic attack parameters]
```

### Positional Arguments

| Argument | Required | Description |
| --- | --- | --- |
| `attack_id` | yes | Attack ID from the catalog. Use `list` to discover valid values. |

### Main Parameters

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--target IP_OR_HOST` | no | none | Generic target alias. Mapped to the selected attack's target parameter, such as `target_ip`, `target_net`, `target`, `target_server`, or `host`. |
| `--port PORT` | no | none | Generic port alias. Mapped to the selected attack's port parameter, commonly `target_port`. |
| `--duration SECONDS` | no | none | If set, the CLI blocks for the requested duration and then stops the attack container automatically. If the attack has a `duration_s` parameter, this value is also resolved into that parameter unless explicitly provided. |
| `--rate PPS` | no | none | Generic rate alias. If the attack has `rate_pps`, this value is resolved into it unless explicitly provided. The container also receives `RATE` and `RATE_PPS` environment variables. |

### Dynamic Attack Parameters

Any additional `--key value` pair can be passed after the static options. The command stores unknown arguments and resolves them against the selected attack metadata.

Example:

```bash
python3 attackzoo.py run recon_ping_sweep --target_net 172.17.0.0/16
```

or with aliases:

```bash
python3 attackzoo.py run bf_ssh --target 127.0.0.1 --port 2222 --duration 20
```

### Resolution Order

For each attack:

1. Extra dynamic parameters are parsed from `--key value` pairs.
2. `--target` is mapped to the attack's declared target parameter when possible.
3. `--port` is mapped to the attack's declared port parameter when possible.
4. `--duration` is copied to `duration_s` when the attack declares it.
5. `--rate` is copied to `rate_pps` when the attack declares it.
6. Defaults from `attack.yaml` are filled.
7. Required parameters are checked.
8. Parameter validation is applied.
9. Positional Docker arguments and environment variables are built from metadata.
10. The attack container is started detached through Docker.

### Behavior

Without `--duration`, `run` starts the container and returns immediately.

With `--duration`, `run` waits, then removes the container:

```text
[OK] Container started: <container_id> duration=10s
[INFO] Waiting 10s... (Ctrl+C to stop early)
[OK] Stopped: <container_name>
```

### Exit Codes

| Code | Meaning |
| --- | --- |
| `0` | Container was started successfully; if `--duration` was used, stop also completed or warning was emitted. |
| `1` | Unknown attack, missing required parameter, validation failure, or Docker run failure. |

## Command: `features`

Extracts feature CSVs from a PCAP.

```bash
python3 attackzoo.py features --pcap FILE [--tools LIST] [--outdir DIR]
```

### Parameters

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--pcap FILE` | yes | none | Input PCAP file. The command fails if the file does not exist. |
| `--tools LIST` | no | `ntlflowlyzer,tshark,scapy` | Comma-separated feature extractors to run. Supported values are `ntlflowlyzer`, `tshark`, and `scapy`. |
| `--outdir DIR` | no | `features` | Directory where feature CSVs are written. |

### Output Filenames

For a PCAP named `example.pcap`, outputs are:

```text
<outdir>/ntlflowlyzer-example.csv
<outdir>/tshark-example.csv
<outdir>/scapy-example.csv
```

Only selected tools are run.

### Tool Behavior

| Tool | Output type | Notes |
| --- | --- | --- |
| `ntlflowlyzer` | Flow-level CSV | Requires `ntlflowlyzer` in `PATH`. The CLI writes a temporary config file under `.tmp/`. If a truncated PCAP error is detected, AttackZoo tries to sanitize the PCAP with `tshark` or `editcap` and retry. |
| `tshark` | Packet-level CSV | Requires `tshark`. Extracts fields such as frame number, timestamp, frame length, protocol, Ethernet/IP addresses, TCP/UDP ports, and TCP flags. |
| `scapy` | Packet-level CSV | Requires Python `scapy`. Reads packets through `PcapReader` and writes normalized packet fields. |

### JSON Result

The command prints JSON with one entry per requested tool. Entries include:

- `ok`;
- `returncode` when applicable;
- `stdout` or `stderr`;
- `cmd`;
- `output`;
- tool-specific metadata such as temporary config paths or sanitized PCAP hints.

Exit codes:

| Code | Meaning |
| --- | --- |
| `0` | Command completed and printed tool results. Individual tools may still report `ok=false` in JSON. |
| `2` | Input PCAP does not exist. |

## Command: `dataset`

Builds an unsupervised dataset CSV from previously generated feature CSVs.

```bash
python3 attackzoo.py dataset --pcap FILE [--features-dir DIR] [--outdir DIR]
```

### Parameters

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--pcap FILE` | yes | none | Input PCAP used to infer feature CSV names. The file must exist. |
| `--features-dir DIR` | no | `features` | Directory containing `ntlflowlyzer-<base>.csv`, `tshark-<base>.csv`, and/or `scapy-<base>.csv`. |
| `--outdir DIR` | no | `datasets` | Directory where the output dataset is saved. |

### Feature Discovery

For `example.pcap`, the command looks for:

```text
<features-dir>/ntlflowlyzer-example.csv
<features-dir>/tshark-example.csv
<features-dir>/scapy-example.csv
```

At least one non-empty feature CSV must exist.

### Normalization

The dataset builder detects source tools and normalizes common fields:

| Normalized column | Meaning |
| --- | --- |
| `ts` | Timestamp when available. |
| `bytes` | Byte count when available. |
| `src_ip` | Source IP for packet-level sources. |
| `dst_ip` | Destination IP for packet-level sources. |
| `proto` | Protocol number or normalized protocol value. |
| `src_port` | Source port when available. |
| `dst_port` | Destination port when available. |
| `pkts` | Packet count, set to `1` for packet-level sources. |
| `source_tool` | Source extractor type, such as `tshark_packets`, `scapy_packets`, or `ntlflowlyzer`. |
| `__source_csv` | Original feature CSV filename. |

### Output

The command saves:

```text
<outdir>/unsupervised-<base>.csv
```

and prints the saved path.

Exit codes:

| Code | Meaning |
| --- | --- |
| `0` | Dataset was generated. |
| `2` | Input PCAP does not exist. |

If no feature CSV is found, the underlying dataset builder raises an error.

## Command: `experiment`

Runs a structured experiment for one attack across one or more intensity levels and repeated runs. Each run can collect probes, PCAPs, host resources, Docker container telemetry, feature CSVs, datasets, and reports.

```bash
python3 attackzoo.py experiment --attack-id ATTACK_ID --out OUT [options]
```

Results are saved under:

```text
experiments/<out>/<attack_id>/<level>/run<N>/
```

Reports are saved under:

```text
experiments/<out>/reports/
```

### Identity Parameters

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--attack-id ATTACK_ID` | yes | none | Attack ID to execute. Must exist in the catalog. |
| `--out OUT` | yes | none | Subdirectory under `experiments/` where the experiment is saved. |
| `--service SERVICE` | no | `--out` value | Service label used for PCAP naming and `{service}` hook substitution. |

### Timing Parameters

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--runs RUNS` | no | `10` | Number of runs per level. Each level gets `RUNS` repetitions. |
| `--warmup WARMUP` | no | `60` | Warmup duration in seconds. |
| `--attack ATTACK` | no | `120` | Attack-window duration in seconds. |
| `--cooldown COOLDOWN` | no | `60` | Cooldown duration in seconds. |
| `--interval INTERVAL` | no | `0.5` | Interval between availability probe samples, in seconds. |
| `--probe-timeout PROBE_TIMEOUT` | no | `2.0` | Per-probe timeout, in seconds. |

Total planned runtime before post-processing is approximately:

```text
runs * number_of_levels * (warmup + attack + cooldown)
```

### Levels

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--levels LEVELS` | no | `L0,L1,L2,L3` | Comma-separated intensity levels. `L0` is baseline and does not call attack hooks. Other names are accepted as text, but reports and conventions assume levels such as `L0`, `L1`, `L2`, and `L3`. |

Example:

```bash
--levels L0,L2
```

### Capture Parameters

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--iface IFACE` | no | `lo` | Network interface passed to `tcpdump -i`. |
| `--bpf BPF` | no | `tcp port 8080 or tcp port 1883` | BPF filter appended to the `tcpdump` command. |

AttackZoo starts:

```text
tcpdump -i <iface> -U -s 0 -w <pcap_path> <bpf tokens>
```

`-U` writes packets as they arrive and `-s 0` captures full packets.

If `tcpdump` is not found, the run continues without PCAP capture and emits a warning.

Per-run PCAP path:

```text
experiments/<out>/<attack_id>/<level>/runNN/<service>-<attack_id>-<level>-runNN.pcap
```

### Probe Parameters

Availability probes run concurrently with the experiment and write one CSV per probe service.

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--probes PROBES` | no | `http,mqtt` | Comma-separated probe services. Use `all` for every supported probe, or `none` to disable probes while still running capture/experiment flow. |
| `--http-url HTTP_URL` | no | `http://127.0.0.1:8080/` | Default endpoint for the HTTP probe. |
| `--https-url HTTPS_URL` | no | `https://127.0.0.1:8443/` | Default endpoint for the HTTPS probe. |
| `--mqtt-host MQTT_HOST` | no | `127.0.0.1` | Default MQTT probe host. |
| `--mqtt-port MQTT_PORT` | no | `1883` | Default MQTT probe port. |
| `--probe-host PROBE_HOST` | no | empty | Default host for non-HTTP/MQTT probes. Falls back to `--host`. |
| `--probe-port PROBE_PORT` | no | `0` | Default port for non-HTTP/MQTT probes. `0` means use service default port. |
| `--probe-endpoint PROBE_ENDPOINT` | no | none | Repeatable endpoint override in the form `service=host:port` or `service=url`. |

Supported probe services:

| Probe | Default port | Behavior |
| --- | ---: | --- |
| `http` | `80` | Performs an HTTP request and reads a small response. |
| `https` | `443` | Performs an HTTPS request with a permissive TLS context for availability checking. |
| `ssh` | `22` | Opens TCP and checks for an `SSH-` banner. |
| `smb` | `445` | Sends a minimal SMB negotiate request. |
| `mqtt` | `1883` | Sends an MQTT 3.1.1 CONNECT and checks CONNACK. |
| `coap` | `5683` | Sends a confirmable CoAP GET request. |
| `xrce` | `8888` | Sends a lightweight UDP datagram for Micro XRCE-DDS reachability. |
| `zenoh` | `7447` | Opens a TCP connection. |
| `telnet` | `23` | Opens TCP and optionally reads a small banner. |

Aliases:

| Alias | Normalized probe |
| --- | --- |
| `web` | `http` |
| `ssl` | `https` |
| `tls` | `https` |
| `xrce-dds` | `xrce` |
| `xrcedds` | `xrce` |
| `micro-xrce-dds` | `xrce` |
| `uxrce-dds` | `xrce` |
| `zenoh-pico` | `zenoh` |

Endpoint override examples:

```bash
--probe-endpoint ssh=172.17.0.3:22
--probe-endpoint https=https://127.0.0.1:8443/
--probe-endpoint coap=127.0.0.1:5683
```

Probe CSV path:

```text
experiments/<out>/<attack_id>/<level>/runNN/probe_<service>.csv
```

Probe CSV columns:

| Column | Description |
| --- | --- |
| `service` | Probe service name. |
| `attack_id` | Experiment attack ID. |
| `level` | Current level. |
| `phase` | `warmup`, `attack`, or `cooldown`. |
| `t_epoch` | Unix timestamp. |
| `t_iso` | UTC ISO timestamp. |
| `t_rel_s` | Seconds since run start. |
| `ok` | `1` for success, `0` for failure. |
| `latency_ms` | Probe latency in milliseconds. |
| `error` | Error text when the probe fails. |

### Hook Target Parameters

Hooks use these values for template substitution.

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--host HOST` | no | `127.0.0.1` | Injected as `{host}` in hook templates. |
| `--port PORT` | no | `1883` when absent | Injected as `{port}` in hook templates. |

These do not automatically become attack parameters unless you put them in the hook command.

### Hook Parameters

Hooks let experiments start and stop attacks during the attack phase.

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--attack-start-hook CMD` | no | empty | Shell command template called at the start of the attack window, only for levels other than `L0`. |
| `--attack-stop-hook CMD` | no | empty | Shell command template called at the end of the attack window, only for levels other than `L0`. |

Available template variables:

| Variable | Meaning |
| --- | --- |
| `{service}` | Resolved service label. |
| `{attack_id}` | Current attack ID. |
| `{level}` | Current level. |
| `{host}` | Value of `--host`. |
| `{port}` | Value of `--port`, or `1883` if omitted. |
| `{duration_s}` | Attack-window duration from `--attack`. |
| `{run_dir}` | Current run directory. |

Example:

```bash
--attack-start-hook "python3 attackzoo.py run dos_http_simple --target {host} --port {port}" \
--attack-stop-hook "python3 attackzoo.py stop dos_http_simple"
```

Hook commands are started with `shell=True`, so shell redirection and pipes are possible. Use quotes carefully.

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--extract-features` | no | false | Extracts feature CSVs from each run PCAP after the run finishes. |

| `--tools-tshark` | no | false | Enables TShark extraction. |
| `--tools-scapy` | no | false | Enables Scapy extraction. |

If `--extract-features` is set and none of `--tools-ntl`, `--tools-tshark`, or `--tools-scapy` is selected, all three extractors are attempted.

Feature filenames use the same naming convention as the standalone `features` command.

### Per-Run Metadata

Every run writes:

```text
meta.json
```

Important fields include:

- `service`;
- `attack_id`;
- `level`;
- `run_id`;
- `started_at_utc`;
- `finished_at_utc`;
- phase durations;
- `pcap`;
- `probe_files`;
- `resource_csv`;
- `server_stats_csv`;
- probe services and endpoints;
- capture interface and BPF;
- hook commands;
- feature extraction results;
- dataset path;
- artifact paths.

### Experiment Reports

After all runs finish, the command writes reports to:

```text
experiments/<out>/reports/
```

It generates:

- availability/probe reports when probe CSVs exist;
- server stats reports when `server_stats.csv` files exist;
- reexecution, stability, and artifact-validity metrics.

### Exit Codes

| Code | Meaning |
| --- | --- |
| `0` | Experiment completed. |
| `1` | Unknown attack ID. |
| `2` | Probe endpoint parsing error. |

## Command: `report`

Regenerates reports from an existing experiment directory.

```bash
python3 attackzoo.py report --input DIR --warmup W --attack A --cooldown C [--outdir DIR]
```

### Parameters

| Parameter | Required | Default | Description |
| --- | --- | --- | --- |
| `--input INPUT` | yes | none | Experiment base directory containing run outputs. The command searches recursively for `probe_*.csv`, `probe.csv`, `server_stats.csv`, and `resource.csv`. |
| `--outdir OUTDIR` | no | `<input>/reports` | Directory where regenerated reports are written. |
| `--warmup WARMUP` | yes | none | Warmup duration used to interpret phase windows. |
| `--attack ATTACK` | yes | none | Attack duration used to interpret phase windows. |
| `--cooldown COOLDOWN` | yes | none | Cooldown duration used to interpret phase windows. |

### Behavior

The command:

1. verifies that `--input` exists;
2. searches recursively for data files, excluding paths under existing `reports`;
3. generates availability reports when probe files exist;
4. generates Docker server stats reports when `server_stats.csv` files exist;
5. generates reexecution, stability, and artifact metrics;
6. prints the output directory.

Exit codes:

| Code | Meaning |
| --- | --- |
| `0` | Reports were generated. |
| `2` | Input directory does not exist or no supported data files were found. |

## Operational Notes

### Choosing Interfaces And BPF Filters

For host-exposed services, useful interfaces include:

- `lo` for loopback traffic such as `127.0.0.1:8080`;
- `docker0` for bridge traffic involving container IPs;
- `any` when a broad capture is desired.

Examples:

```bash
--iface lo --bpf "tcp port 8080"
--iface docker0 --bpf "host 172.17.0.2 and tcp port 80"
--iface any --bpf "tcp port 1883 or udp port 5683"
```

### Probe Selection Strategy

Use probes that match the target service under observation. For example:

```bash
--probes http --http-url http://127.0.0.1:8080/
--probes ssh --probe-endpoint ssh=127.0.0.1:2222
--probes mqtt --mqtt-host 127.0.0.1 --mqtt-port 1883
--probes none
```

Use `--probes none` when the experiment should focus only on PCAP capture and artifact generation.

### Direct Runs Versus Experiments

Use `run` when you want to start one attack container manually.

Use `experiment` when you need:

- repeated runs;
- level-based comparisons;
- warmup/attack/cooldown phases;
- PCAP capture;
- concurrent availability probes;
- telemetry CSVs;
- generated features/datasets;
- final reports.

### Safety

Many catalog entries are scanners, brute-force tools, fuzzers, or flood attacks. Run them only in isolated environments that you own and are authorized to test. Prefer short durations and local target containers for validation.

## Quick Reference

```bash
# Check Docker availability
python3 attackzoo.py status

# List attacks
python3 attackzoo.py list
python3 attackzoo.py list --json
python3 attackzoo.py list --id bf_ssh

# Run and stop attacks
python3 attackzoo.py run bf_ssh --target 127.0.0.1 --port 2222 --duration 10
python3 attackzoo.py stop bf_ssh
python3 attackzoo.py ps --all
python3 attackzoo.py logs bf_ssh --tail 100

# Captures, features, datasets
python3 attackzoo.py captures --latest
python3 attackzoo.py features --pcap captures/example.pcap --tools tshark,scapy
python3 attackzoo.py dataset --pcap captures/example.pcap

# Experiment
python3 attackzoo.py experiment \
  --attack-id dos_http_simple \
  --out full_http \
  --runs 3 \
  --levels L0,L1 \
  --warmup 30 \
  --attack 60 \
  --cooldown 30 \
  --probes http \
  --http-url http://127.0.0.1:8080/ \
  --iface lo \
  --bpf "tcp port 8080" \
  --collect-resources \
  --extract-features \
  --build-dataset

# Regenerate reports
python3 attackzoo.py report \
  --input experiments/full_http \
  --warmup 30 \
  --attack 60 \
  --cooldown 30
```
